# Python dependencies

The active workflow has two execution profiles:

- CPU FV generation: NumPy, SciPy, Joblib, and Matplotlib;
- Model training/validation: the CPU stack plus JAX, Optax, `soap-jax`,
  Equinox, Optimistix, and tqdm. Runs on CPU; GPU is optional and only
  changes performance.

The project does not require Warp, cuDSS, CuPy, PyTorch, or MPI for the active
scripts. JAX is used for neural-network training and automatic differentiation;
the FV labels are generated by the CPU solver outside JAX.

## Environment

The environment is self-contained inside `SlabRpfPinn/`, on the local machine
and on every HPC cluster. Never activate an environment outside this
directory — see [`docs/PROJECT_CONTEXT.md`](PROJECT_CONTEXT.md).

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
pip install "git+https://github.com/haydn-jones/SOAP_JAX"
pip install "git+https://github.com/raj-brown/optimistix.git@feature/ss-quasi-newton"
python -c 'import sys; print(sys.executable)'
```

`soap-jax` on PyPI is an unrelated package (name collision with a Java
SOAP/JAX-WS project); it does not provide the `soap_jax` module this project
imports. Install the actual SOAP optimizer implementation directly from its
git source, `haydn-jones/SOAP_JAX`, as shown above.

Plain `optimistix` from PyPI (pulled in by `requirements.txt`) does not
provide `AbstractSSBroyden`/`SSBroyden`, used by the SSBroyden refinement
loop in `core/training.py`. Install the SS-Quasi-Newton fork,
`raj-brown/optimistix.git@feature/ss-quasi-newton`, per
[`CrunchOptimizer/PINNs`](https://github.com/CrunchOptimizer/PINNs), as shown
above; it replaces plain `optimistix` (and downgrades its `jax`, `jaxlib`,
`equinox`, and `lineax` pins — see Version policy below).

`requirements.txt` lists the base/CPU stack plus plain `jax`, which runs on
CPU as-is. For GPU (optional, performance only) on Perlmutter (CUDA 13
GPUs), replace the plain `jax` install with the CUDA-matched plugin:

```bash
pip install "jax[cuda13]"
```

Use the cluster-specific Python module documented in
[`PERLMUTTER.md`](PERLMUTTER.md) to create `.venv`, then activate `.venv`
(not a module-provided environment) for the run. Keep the environment
outside generated datasets and model runs. Do not install dependencies into
the repository during a production run.

## Required imports

Check the complete import set after installing or changing the environment:

```bash
python - <<'PY'
import equinox
import joblib
import jax
import matplotlib
import numpy
import optax
import optimistix
import scipy
import soap_jax
import tqdm

print("JAX:", jax.default_backend(), jax.devices())
print("FP64:", jax.config.jax_enable_x64)
print("SSBroyden:", hasattr(optimistix, "AbstractSSBroyden"))
PY
```

Training, validation, and dataset generation all run correctly on a CPU
backend; GPU only changes speed. Do not treat a login-node import as evidence
that a GPU backend is usable, even if requested — always confirm inside an
allocation.

## Version policy

Pin versions in the environment rather than in the repository drivers. JAX,
its CUDA plugin, and the NVIDIA driver must be a compatible set for the target
cluster. Keep a package export or environment lockfile with production runs.
The scripts enable JAX FP64 and disable memory preallocation before importing
JAX; these settings are part of the numerical/runtime contract.

The SS-Quasi-Newton `optimistix` fork pins an older `jax`/`jaxlib` (0.4.38)
and downgrades `equinox` and `lineax` to match. This produces `pip` dependency
warnings against `optax`/`chex`, which declare newer minimum `jax` versions;
imports and `optx.minimise` construction still work under this pin set on
CPU (verified on this project's CPU backend). Reinstalling plain `optax`
after the fork will re-upgrade `jax` and reintroduce the missing
`AbstractSSBroyden`/`SSBroyden` problem — always install `optimistix` from
the fork last, as ordered above.

## Multi-node requirements

Data/DeepONet training uses JAX multi-host initialization through Slurm and
requires:

- one visible local GPU set per node;
- one Slurm task per node;
- passwordless host reachability between allocated nodes;
- a shared filesystem for the dataset, run directory, and synchronization
  markers;
- `scontrol show hostnames` available to the launcher.

CPU FV generation uses one process per node and Joblib workers within each
process. SOAP physics training uses the same one-process-per-node JAX launch;
multi-node SSBroyden is executed on rank 0 and then broadcast.
